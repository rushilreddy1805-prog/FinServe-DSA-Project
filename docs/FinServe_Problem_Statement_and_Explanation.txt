 1. PROBLEM STATEMENT  (WHAT PROBLEM OUR PROJECT SOLVES)
--------------------------------------------------------------------------------

Banks deal with a LOT of data every single second:

   - customer details
   - account numbers and balances
   - money transfers and transactions
   - documents, remarks and descriptions (free text)
   - fraud warnings and risk signals

Doing all this work with simple, slow methods (loops inside loops) becomes very
slow when the data grows. So the real problem is:

   "How can we use classic Data Structures and Algorithms (DSA) to solve common
    banking problems QUICKLY, CORRECTLY and with LOW memory?"

Our project, FINSERVE, solves this by building one menu-driven Java program that
takes realistic banking tasks and solves each one with the right algorithm.

The concrete problems we solve are:

   P1. Find a code/word (like "NEFT", "IMPS") inside huge text quickly.
   P2. Find MANY fraud keywords in one pass over a document.
   P3. Build a fast "index" so we can search inside documents again and again.
   P4. Find the longest phrase that repeats in transaction remarks.
   P5. Fix spelling mistakes in transaction descriptions automatically.
   P6. Assign analysts to fraud cases in the cheapest way.
   P7. Decide the cheapest order to run a chain of operations.
   P8. Find how much money can flow through a network of accounts (max flow)
       and find the bottleneck channels (min cut).
   P9. Check whether a set of financial rules can all be satisfied together.
   P10. Find groups that are fully compatible (clique) or fully conflicting
        (independent set), and the smallest set that covers all links.
   P11. Rank transactions by amount/risk, test if a big number is prime, take a
        fair random sample from a live stream, and add up amounts in parallel.

So in ONE line: FinServe turns real banking work into 26 well-known DSA
algorithms across 6 modules, and shows that the right algorithm makes the job
fast, exact and memory-friendly.

--------------------------------------------------------------------------------
 2. FROM WHERE DO WE TAKE THE DATA SET?
--------------------------------------------------------------------------------

We do NOT download data from the internet and we do NOT use any database.

All the data is created INSIDE the program by one file:
        src/finserve/util/DataStore.java

DataStore builds everything in memory (RAM) when the program starts:

   - 8 Customers        : C001 .. C008  (id, name, city, risk score)
   - 8 Accounts         : ACC1001 .. ACC1008 (owner, balance, type)
   - 10 Transactions    : TXN0001 .. TXN0010 (from, to, amount, description,
                          timestamp, currency, status)
   - 3 Documents        : DOC001 .. DOC003 (title + text content)
   - 5 Fraud Patterns   : keyword phrases like "cash deposit",
                          "structured withdrawal", "high risk transfer"
   - Graph generators   : code that makes the transaction network (accounts as
                          nodes, money as capacity) for Module 4.

Why in memory?  => The project must run anywhere with no setup. Anyone can just
double-click run.bat and see full output instantly. No server, no install.

It is realistic dummy/sample financial data written by us, so it is safe to show
and easy to change.

--------------------------------------------------------------------------------
 3. HOW DO WE UPDATE THE DATA SET?
--------------------------------------------------------------------------------

There are TWO easy ways:

 (A) STATIC UPDATE (change the seed data in code):
       Open  src/finserve/util/DataStore.java
       - add/remove a customer, account, transaction, document or fraud pattern
         in the lists there
       - save the file
       - run  build.bat  (or run.bat) to rebuild
     The new data now appears everywhere automatically (menus, data screen,
     searches, flows).

 (B) LIVE / RUNTIME UPDATE (type your own data while the program runs):
       Most menu options ask you for input and offer a default value:
       - M1: type your own text and pattern
       - M2: type your own document text
       - M3: type two descriptions, costs, sizes of operations
       - M5: type your own rule formula (e.g.  1 2 -3 | -1 3 4 | -2 -4 1 )
       - M6: type your own array, number, sample size, W/D/P values
       If you press ENTER without typing, the program uses the sample data, so
       it never gets stuck.

 Note: The Module-4 network is generated from a FIXED random seed (2026), so the
 same flow/cut results appear every run. That makes results repeatable for the
 viva. If you want a different network, change the seed number in the code.

 4. WHICH MODULE DOES WHAT  (AND THE MENU EXPLANATION)
--------------------------------------------------------------------------------

The project has 6 modules, matching the 6 course outcomes (CO1..CO6).

-------------------------------------------------------------------------------
 MAIN MENU
-------------------------------------------------------------------------------
   1. Search & detect things in text      [Module M1]  -> string algorithms
   2. Build an index to look things up    [Module M2]  -> suffix structures
   3. Fix errors & plan operations        [Module M3]  -> dynamic programming
   4. Route money & assign work           [Module M4]  -> network flow
   5. Check rules & find groups           [Module M5]  -> NP / approximation
   6. Rank, sample & speed up             [Module M6]  -> randomized & parallel
   7. Show Banking Data                   -> prints all seed data
   8. About FinServe                      -> short project summary
   0. Exit                                -> quits the program

-------------------------------------------------------------------------------
 MODULE 1  -  SEARCH & DETECT IN TEXT  (CO1)
-------------------------------------------------------------------------------
 Menu:
   1. Find a payment/transaction code in text      (KMP)
   2. Find a repeated pattern in descriptions      (Z-Function)
   3. Find a financial code using fast hashing     (Rabin-Karp)
   4. Find many fraud patterns in a single scan     (Aho-Corasick)
 Does: looks for a word/code inside text. Option 4 scans once and reports ALL
       fraud patterns together.

-------------------------------------------------------------------------------
 MODULE 2  -  BUILD AN INDEX TO LOOK THINGS UP  (CO2)
-------------------------------------------------------------------------------
 Menu:
   1. Build a searchable index of descriptions     (Suffix Array)
   2. Build an index for large documents very fast (SA-IS)
   3. Find the longest repeated phrase             (Kasai LCP)
   4. Check whether a phrase exists and how often  (Suffix Automaton)
 Does: prepares the text once so later searches are very fast; also mines
       repeated phrases.

-------------------------------------------------------------------------------
 MODULE 3  -  FIX ERRORS & PLAN OPERATIONS  (CO3)
-------------------------------------------------------------------------------
 Menu:
   1. Measure/correct how different two texts are  (Levenshtein / Damerau)
   2. Compare codes where some mistakes cost more   (Weighted Edit Distance)
   3. Assign cases to analysts at lowest cost        (Bitmask DP)
   4. Find the cheapest order to run operations      (Matrix-Chain)
 Does: compares/corrects text and finds optimal plans with the least cost.

-------------------------------------------------------------------------------
 MODULE 4  -  ROUTE MONEY & ASSIGN WORK  (CO4)
-------------------------------------------------------------------------------
 Menu:
   1. How much money can flow through the network  (Ford-Fulkerson)
   2. Same, using the shortest-path method         (Edmonds-Karp)
   3. Same, for large networks                     (Dinic)
   4. Assign analysts to fraud cases               (Bipartite Matching)
   5. Find the bottleneck (critical) channels       (Min-Cut)
 Does: models accounts as a network and finds max flow and the weak links.
       Options 1-3 give the SAME max flow (a nice correctness proof).

-------------------------------------------------------------------------------
 MODULE 5  -  CHECK RULES & FIND GROUPS  (CO5)
-------------------------------------------------------------------------------
 Menu:
   1. Check whether financial rules can all be satisfied (SAT / 3-SAT)
   2. Turn rule conflicts into a group problem          (3-SAT -> Clique)
   3. Find compatible / conflicting groups              (Clique/Ind-Set/Cover)
   4. Cover every dependency with few control points     (Vertex-Cover 2-approx)
 Does: handles HARD (NP) problems - gives exact answers for small inputs and a
       fast approximate answer with a guarantee for bigger ones.

-------------------------------------------------------------------------------
 MODULE 6  -  RANK, SAMPLE & SPEED UP  (CO6)
-------------------------------------------------------------------------------
 Menu:
   1. Rank transactions quickly                    (Randomized QuickSort)
   2. Check whether a big number is prime          (Miller-Rabin)
   3. Pick a fair random sample from a live stream  (Reservoir Sampling)
   4. Running totals / cumulative statistics        (Blelloch Scan)
   5. Add up all amounts in parallel                (Parallel Reduce)
   6. Estimate parallel speed-up                    (Brent's Theorem)
 Does: sorting, primality testing, random sampling and parallel-style
       aggregation, with analysis of time and speed-up.

 5. ALGORITHMS USED: WHAT IT DOES, WHY THIS, AND WHY NOT THE OTHER
--------------------------------------------------------------------------------

Pick ONE per point:
  [WHAT]      = what the algorithm does (simple words)
  [WHERE/WHY] = where we use it and why we chose it
  [NOT OTHER] = why we did not use a different, common option

====================  MODULE 1 - STRING ALGORITHMS  ====================

1.1 KMP (Knuth-Morris-Pratt)
 [WHAT]      Searches a pattern in text by remembering how much of the pattern
             already matched, so it NEVER moves backwards. It pre-builds a small
             "failure table".
 [WHERE/WHY] Used to find payment codes like NEFT/IMPS. Time O(n+m), always
             exact, no worst-case slowdown.
 [NOT OTHER] Not plain search (O(n*m) - too slow, re-checks letters). Not
             Rabin-Karp (hashing can clash and worst case is O(n*m)).

1.2 Z-Function
 [WHAT]      For every position, tells how long a substring starting there
             matches the prefix of the string. Matching uses "pattern$text".
 [WHERE/WHY] Good for spotting repeated/periodic structures in descriptions.
 [NOT OTHER] Both KMP and Z are linear; we include Z because it directly shows
             repetition (a different, useful view of the same problem).

1.3 Rabin-Karp
 [WHAT]      Uses a rolling HASH of the pattern and of each text window; only
             checks letters when hashes match. The window hash updates in O(1).
 [WHERE/WHY] Useful when many patterns share the same length, or to filter
             candidates fast by hash before a full compare.
 [NOT OTHER] Not KMP here because hashing lets us reuse one computation across
             many windows/patterns; KMP cannot share work that way. (We kept KMP
             too, so we can compare exact vs hashed search.)

1.4 Aho-Corasick
 [WHAT]      Builds a TRIE of many patterns, adds "failure links" (like KMP but
             for a whole set), and scans the text ONCE reporting all matches.
 [WHERE/WHY] Detecting all fraud keywords in one pass. Cost O(n + matches).
 [NOT OTHER] Not "run KMP once per pattern" - that is O(k*(n+m)) and wasteful.
             One automaton, one scan, all patterns - much faster.

====================  MODULE 2 - SUFFIX STRUCTURES  ====================

2.1 Suffix Array (prefix doubling)
 [WHAT]      A sorted list of all suffix start positions of a text. To search a
             substring, use binary search on this list.
 [WHERE/WHY] Indexing transaction descriptions so repeated searches are fast.
 [NOT OTHER] Not a suffix TREE: the tree is bigger and more complex; the array
             uses less memory (O(n)) and is easier to code.

2.2 SA-IS (Suffix Array Induced Sorting)
 [WHAT]      Builds the same suffix array but in LINEAR time O(n), using L/S
             types and induced sorting instead of comparison sorting.
 [WHERE/WHY] For very large documents where O(n log n) is too slow.
 [NOT OTHER] Not the doubling method (O(n log^2 n)). SA-IS is optimal O(n), the
             same algorithm used inside real search engines. (We still keep
             doubling for comparison and as a correctness check.)

2.3 Kasai LCP
 [WHAT]      Computes, between neighbouring suffixes in the array, the length of
             their longest common prefix - in O(n). Also finds the longest
             repeated substring.
 [WHERE/WHY] Mines repeated phrases in transaction remarks.
 [NOT OTHER] Not comparing every pair of suffixes (O(n^2) - far too slow).

2.4 Suffix Automaton
 [WHAT]      A minimal machine (DFA) that represents ALL substrings in O(n)
             states; answers "does it contain X?" and "how many times?" fast.
 [WHERE/WHY] Fast, repeated substring/occurrence queries on documents.
 [NOT OTHER] Not the suffix array here because the automaton is built ONLINE and
             each query is just O(length of pattern), very convenient for many
             queries and for counting occurrences.

====================  MODULE 3 - DYNAMIC PROGRAMMING  ====================

3.1 Levenshtein / Damerau-Levenshtein
 [WHAT]      Minimum number of insert/delete/replace edits to change one string
             into another. Damerau also allows swapping two neighbours. It can
             even print the actual edits.
 [WHERE/WHY] Correcting misspelled transaction descriptions; finding near
             duplicates.
 [NOT OTHER] Not Hamming distance (that only replaces and needs equal length).
             We need insert/delete too, so Levenshtein is the right metric.

3.2 Weighted Edit Distance
 [WHAT]      Same idea, but insert, delete and replace have DIFFERENT costs.
             The digit-aware version charges the difference between digits.
 [WHERE/WHY] In banking, some mistakes cost more than others (1->2 is a cheaper
             error than 1->9).
 [NOT OTHER] Not plain Levenshtein because it assumes every mistake costs the
             same, which is not realistic for numeric financial data.

3.3 Bitmask DP
 [WHAT]      Uses bitmasks (0/1 flags) to represent "which cases are taken".
             dp[mask] = cheapest way to cover that set; also solves a small
             "best value within budget" selection.
 [WHERE/WHY] Assign analysts to cases at the least total cost. Exact for small n.
 [NOT OTHER] Not the Hungarian method (O(n^3)): bitmask DP is simpler, easier to
             explain, and ALSO gives subset/knapsack solutions. For small inputs
             it is perfectly fast.

3.4 Matrix-Chain Multiplication
 [WHAT]      Finds the order of multiplying a chain of matrices that uses the
             fewest number of multiplications; also prints that order.
 [WHERE/WHY] Ordering a chain of analysis operations (each modelled as a
             matrix).
 [NOT OTHER] Not a greedy choice: greedy "multiply the smallest first" is NOT
             always optimal. DP checks all split points and guarantees the best.

====================  MODULE 4 - NETWORK FLOW  ====================

4.1 Ford-Fulkerson
 [WHAT]      Keeps finding ANY path from source to sink with spare capacity and
             pushes flow, until no path is left. That total is the max flow.
 [WHERE/WHY] Shows how much money can be routed through the account network.
 [NOT OTHER] Not a single greedy pass (it can get stuck). We must use the
             residual graph with back-edges so earlier choices can be undone.

4.2 Edmonds-Karp
 [WHAT]      Same as Ford-Fulkerson but always picks the SHORTEST path (using
             BFS), which guarantees it finishes in polynomial time.
 [WHERE/WHY] When FF might take too long.
 [NOT OTHER] Not plain FF for worst-case safety: FF time depends on the flow
             value, EK does not.

4.3 Dinic
 [WHAT]      Builds a "level graph" (BFS) and pushes a whole "blocking flow" at
             once (DFS). Very fast on real networks.
 [WHERE/WHY] Larger transaction networks.
 [NOT OTHER] Not EK for large graphs: Dinic is faster, O(V^2 E), and even
             O(E*sqrt(V)) on unit-capacity/bipartite graphs.

   NOTE: We show all three because they all give the SAME max flow -> strong
         proof that our implementations are correct.

4.4 Bipartite Matching (Kuhn's algorithm)
 [WHAT]      Matches as many analysts as possible to the cases they qualify for,
             using augmenting paths.
 [WHERE/WHY] Assigning people to fraud cases. Polynomial O(V*E).
 [NOT OTHER] Not Bitmask DP here: bitmask assignment is exponential and only for
             small numbers. Matching scales to many analysts/cases.

4.5 Min-Cut
 [WHAT]      After a max-flow run, the channels that are "full" form the minimum
             cut - the bottlenecks. By the max-flow min-cut theorem, cut value =
             max flow.
 [WHERE/WHY] Finding the critical channels whose removal blocks all payments.
 [NOT OTHER] We do NOT need a separate expensive algorithm: it comes FREE from
             the max-flow computation in O(V+E) extra time.

====================  MODULE 5 - NP-COMPLETENESS / APPROXIMATION  ==========

5.1 SAT / 3-SAT (DPLL)
 [WHAT]      Checks if Boolean rules can all be true together. DPLL uses unit
             propagation and smart branching to avoid checking every case.
 [WHERE/WHY] Financial-rule constraints (e.g. "if KYC missing then block OR
             flag review").
 [NOT OTHER] Not brute force over 2^n assignments: DPLL prunes most branches and
             is much faster in practice (still exponential in the worst case,
             because SAT is NP-complete). We keep brute force only as a
             correctness check.

5.2 3-SAT -> CLIQUE
 [WHAT]      Turns the rule formula into a graph (3 nodes per rule, edges between
             compatible conditions). The formula is satisfiable exactly when the
             graph has a clique the size of the number of rules.
 [WHERE/WHY] Demonstrates a classic NP-completeness reduction.
 [NOT OTHER] This reduction IS the point of the module - there is no simpler
             substitute; it proves the problem is hard.

5.3 CLIQUE -> INDEPENDENT-SET -> VERTEX-COVER
 [WHAT]      A clique in graph G = an independent set in the complement of G;
             a vertex cover is the complement of an independent set. So solving
             one solves all three.
 [WHERE/WHY] Shows the famous reduction chain for NP-hard graph problems.
 [NOT OTHER] Again the chain itself is what we must demonstrate.

5.4 Vertex-Cover 2-approximation
 [WHAT]      Greedily take BOTH ends of each edge of a maximal matching. The
             result is at most 2x the true minimum, in O(V+E).
 [WHERE/WHY] Covering dependencies fast when the exact answer is too slow.
 [NOT OTHER] Not the exact solver for large inputs: exact is exponential.
             Approximation trades a small quality loss (<= 2x) for polynomial
             speed - a proven guarantee.

====================  MODULE 6 - RANDOMIZED / PARALLEL  ====================

6.1 Randomized QuickSort
 [WHAT]      Sorts by picking a RANDOM pivot and splitting into three parts
             (less / equal / greater). Counts comparisons and depth.
 [WHERE/WHY] Ranking transactions by amount/risk. Expected O(n log n).
 [NOT OTHER] Not plain QuickSort with a fixed pivot: an attacker (or sorted
             input) can force O(n^2). A random pivot makes the expected time
             O(n log n) for every input. (Merge sort is also fine, but quicksort
             shows the power of randomization and sorts in place.)

6.2 Miller-Rabin
 [WHAT]      A fast test that says whether a big number is prime, using a few
             "witness" bases. For 64-bit numbers it is exact; for huge numbers
             the error chance is at most 2^-k.
 [WHERE/WHY] Large-number / cryptography-style computations.
 [NOT OTHER] Not trial division: that needs O(sqrt n) checks - hopeless for big
             numbers. Miller-Rabin is logarithmic in n and extremely reliable.

6.3 Reservoir Sampling
 [WHAT]      Picks k items uniformly from a stream of unknown length in ONE pass
             using only O(k) memory.
 [WHERE/WHY] Taking a fair sample from a continuous transaction stream.
 [NOT OTHER] Not "store everything then sample": that uses O(n) memory. The
             reservoir keeps memory constant and needs only one pass.

6.4 Blelloch Scan
 [WHAT]      A parallel prefix sum: an up-sweep (reduce) then a down-sweep, on
             an array padded to a power of two.
 [WHERE/WHY] Running/cumulative totals of transactions.
 [NOT OTHER] Not a simple sequential loop: the parallel version has O(n) work
             and only O(log n) depth, which is the model of a parallel primitive.

6.5 Parallel Reduce
 [WHAT]      Adds numbers in a tree shape, level by level, and shows the work
             (n-1) and depth (log n).
 [WHERE/WHY] Totalling financial volume.
 [NOT OTHER] Same reason: shows how a loop becomes a parallel tree with small
             depth.

6.6 Brent's Theorem
 [WHAT]      A formula: T_P <= W/P + D (time <= work/processors + depth). It
             also gives speed-up and efficiency.
 [WHERE/WHY] Estimating how much faster parallel processing can be.
 [NOT OTHER] Not just timing code: Brent's theorem gives a THEORETICAL bound
             from work and depth - the correct way to analyse parallel
             algorithms.
