--------------------------------------------------------------------------------
 1. WHAT IS THIS PROJECT?
--------------------------------------------------------------------------------

FinServe is a banking and financial analytics platform that models and processes:

   * Customer and account information
   * Financial transactions and payment records
   * Fraud indicators and security events
   * Financial documents and reports
   * Continuous transaction streams
   * Resource and transaction-processing constraints

It is implemented as an INTERACTIVE, MENU-DRIVEN COMMAND-LINE APPLICATION in
pure Java (no frameworks, no external libraries, no UI/CSS). The whole project
is a single Java codebase whose purpose is to demonstrate 26 classic DSA
algorithms and data structures mapped onto realistic banking problems.

The project is divided into six modules (M1..M6), exactly matching the six
course outcomes (CO1..CO6):

   M1 - String Algorithms                     (CO1)
   M2 - Suffix Structures                     (CO2)
   M3 - Advanced Dynamic Programming          (CO3)
   M4 - Network Flow                          (CO4)
   M5 - NP-Completeness and Approximation      (CO5)
   M6 - Randomized and Parallel Algorithms    (CO6)

Everything the demo needs (customers, accounts, transactions, documents, fraud
patterns) is generated in memory by DataStore.java, so no database or files are
required to run it.

 2. TECHNOLOGY AND HOW TO RUN
--------------------------------------------------------------------------------

   Language : Java (Java 8 compatible; compiled with --release 8)
   Interface: Console (Scanner) with a numbered menu
   Libraries: Only the Java standard library (java.util, java.math, java.io)

   To run on Windows:
       1. Open the project folder "DSA3 END SEM PROJECT"
       2. Double-click  run.bat   (it compiles and starts the program)

   Or manually:
       javac -d out src\finserve\*.java (compile every .java file under src)
       java  -cp out finserve.Main

   Or open the "src" folder in IntelliJ / Eclipse / VS Code and run the class
   "finserve.Main".

--------------------------------------------------------------------------------
 5. MODULE-BY-MODULE EXPLANATION (WHAT, WHERE, WHY, COMPLEXITY)
--------------------------------------------------------------------------------

====================  MODULE 1 - STRING ALGORITHMS (CO1)  ====================

1.1 KMP  (src/finserve/m1_strings/KMP.java)
    WHAT : Finds every occurrence of a pattern in a text by precomputing the
           longest-proper-prefix-suffix (failure / LPS) array. On a mismatch it
           never re-scans characters it already matched.
    WHERE: Searching transaction / payment codes (e.g. "NEFT", "IMPS") inside
           the transaction-description corpus.
    WHY  : Linear-time searching without backtracking; robust for streaming
           payment-code lookups.
    TIME : O(n + m)   SPACE: O(m)      (n = text length, m = pattern length)

1.2 Z-Function  (src/finserve/m1_strings/ZFunction.java)
    WHAT : Computes for every position i the length of the longest substring
           starting at i that is also a prefix of the string. Matching is done
           via the "pattern $ text" trick.
    WHERE: Detecting repeated transaction-description patterns.
    WHY  : Another linear-time matcher; also directly useful for finding
           periodic / repeated structures.
    TIME : O(n + m)   SPACE: O(n + m)

1.3 Rabin-Karp  (src/finserve/m1_strings/RabinKarp.java)
    WHAT : Compares hash values of the pattern and each text window using a
           rolling hash; verifies character-by-character only on hash matches.
    WHERE: Searching financial codes where many candidates must be filtered
           quickly by hash before a full comparison.
    WHY  : Great for multiple patterns (same window hash) and for plagiarism /
           fingerprint style matching.
    TIME : O(n + m) expected, O(nm) worst case   SPACE: O(1)

1.4 Aho-Corasick  (src/finserve/m1_strings/AhoCorasick.java)
    WHAT : Builds a trie of many patterns, adds failure links (like KMP but for
           a set), and scans the text once reporting ALL pattern matches.
    WHERE: Detecting MULTIPLE fraud patterns ("cash deposit",
           "structured withdrawal", "high risk transfer", ...) in one pass over
           a document.
    WHY  : One machine, one scan, all patterns - far better than running KMP
           once per pattern.
    TIME : O(n + total_matches) after O(sum of pattern lengths) build
    SPACE: O(total pattern length * alphabet)

====================  MODULE 2 - SUFFIX STRUCTURES (CO2)  ====================

2.1 Suffix Array  (src/finserve/m2_suffix/SuffixArray.java)
    WHAT : Array of all suffix start positions in sorted order, built with
           prefix doubling (rank-doubling). Substring search = binary search.
    WHERE: Indexing transaction descriptions.
    WHY  : Compact alternative to suffix trees; enables ranked/range queries.
    TIME : O(n log^2 n) with comparison sort (O(n log n) with radix)
    SPACE: O(n)

2.2 SA-IS  (src/finserve/m2_suffix/SAIS.java)
    WHAT : Suffix Array Induced Sorting - a LINEAR-time suffix array builder
           using L/S types, LMS substrings, and induced sorting (recursive).
    WHERE: Large-scale financial-document indexing where O(n log n) is too slow.
    WHY  : Optimal O(n) construction; the same algorithm used in real text
           search engines.
    TIME : O(n)   SPACE: O(n)
    NOTE : Verified against the naive O(n^2 log n) builder on 14,400 random
           strings with 0 mismatches.

2.3 Kasai LCP  (src/finserve/m2_suffix/KasaiLCP.java)
    WHAT : Computes the LCP array (Longest Common Prefix between adjacent
           suffixes in the suffix array) in linear time. Also returns the
           longest repeated substring.
    WHERE: Mining repeated transaction patterns.
    WHY  : LCP powers repeated-substring, distinct-substring and range queries.
    TIME : O(n)   SPACE: O(n)

2.4 Suffix Automaton  (src/finserve/m2_suffix/SuffixAutomaton.java)
    WHAT : A minimal DFA of all substrings in O(n) states. Supports
           contains(), countOccurrences(), distinctSubstrings(),
           longestRepeatedSubstring().
    WHERE: Fast substring / occurrence queries over a financial document.
    WHY  : Online construction; each substring query is O(|pattern|).
    TIME : O(n) build; O(m) per query   SPACE: O(n) states

====================  MODULE 3 - ADVANCED DYNAMIC PROGRAMMING (CO3)  =========

3.1 Levenshtein / Damerau-Levenshtein  (src/finserve/m3_dp/EditDistance.java)
    WHAT : Minimum number of insert/delete/substitute edits to turn one string
           into another. Damerau variant also allows adjacent transposition.
           A back-trace prints the actual edit operations.
    WHERE: Correcting misspelled transaction descriptions and finding
           near-duplicate financial records.
    WHY  : Standard fuzzy-matching metric; exposes a full DP table.
    TIME : O(n*m)   SPACE: O(min(n,m)) for the distance (O(nm) with backtrace)

3.2 Weighted Edit Distance  (src/finserve/m3_dp/WeightedEditDistance.java)
    WHAT : Edit distance where insert, delete and substitute carry DIFFERENT
           costs; the digit-aware variant charges |digit difference| for
           substituting one digit with another.
    WHERE: Financial-data error handling (e.g. account codes where 1->2 is a
           cheaper error than 1->9).
    WHY  : Real-world correction costs are not uniform.
    TIME : O(n*m)   SPACE: O(n*m)

3.3 Bitmask DP  (src/finserve/m3_dp/BitmaskDP.java)
    WHAT : DP over subsets represented as bitmasks. Provides
           minCostAssignment(cost) - assign N analysts to N cases at minimum
           total cost - and maxValueSubset(value,weight,budget).
    WHERE: Selecting combinations / assignments of financial operations.
    WHY  : Exact optimal matching for small N; a clean introduction to
           subset DP.
    TIME : O(n * 2^n)   SPACE: O(2^n)

3.4 Matrix-Chain Multiplication  (src/finserve/m3_dp/MatrixChain.java)
    WHAT : Finds the parenthesisation that minimises scalar multiplications,
           plus reconstructs the optimal order.
    WHERE: Ordering a chain of transaction-analysis operations (each a matrix).
    WHY  : Classic interval DP; shows optimal-substructure & overlapping
           subproblems.
    TIME : O(n^3)   SPACE: O(n^2)

====================  MODULE 4 - NETWORK FLOW (CO4)  ========================

4.1 Ford-Fulkerson  (src/finserve/m4_flow/FlowNetwork.java)
    WHAT : Repeatedly finds ANY augmenting s-t path (here by DFS) in the
           residual graph and pushes flow, until no path remains.
    WHERE: Transaction-flow analysis (how much money can move through accounts).
    WHY  : Baseline max-flow algorithm; easy to explain.
    TIME : O(E * maxFlow) with integer capacities   SPACE: O(V + E)

4.2 Edmonds-Karp  (same file) - uses BFS to pick the SHORTEST augmenting path.
    TIME : O(V * E^2)   SPACE: O(V + E)

4.3 Dinic's algorithm  (same file) - builds a level graph (BFS) and pushes a
    blocking flow (DFS with current-arc optimisation).
    TIME : O(V^2 * E) general, O(E * sqrt(V)) on unit-capacity / bipartite
    SPACE: O(V + E)

4.4 Bipartite Matching  (src/finserve/m4_flow/BipartiteMatching.java)
    WHAT : Kuhn's augmenting-path algorithm to match the maximum number of
           analysts to fraud cases they are qualified for.
    TIME : O(V * E)   SPACE: O(V + E)

4.5 Min-Cut  (src/finserve/m4_flow/MinCut.java)
    WHAT : After a max-flow run, the set of residual-reachable vertices gives
           the source side; the cut edges are the CRITICAL transaction
           channels. By the max-flow min-cut theorem, cut capacity == max flow.
    TIME : O(V + E) after one max-flow   SPACE: O(V + E)

====================  MODULE 5 - NP-COMPLETENESS / APPROX (CO5)  ============

5.1 SAT / 3-SAT  (src/finserve/m5_np/Sat3.java)
    WHAT : DPLL backtracking solver for CNF formulas: unit propagation +
           variable branching. Includes a brute-force cross-check.
    WHERE: Financial-rule constraints (each clause = "if KYC missing then block
           transfer OR flag review").
    WHY  : SAT is the canonical NP-complete problem.
    TIME : exponential worst case; polynomial on many practical instances.

5.2 3-SAT -> CLIQUE  (src/finserve/m5_np/Clique.java)
    WHAT : Standard reduction: one triangle of 3 vertices per clause; connect
           literals of DIFFERENT clauses unless they are complementary. The
           formula is satisfiable iff the graph has a clique of size = number
           of clauses. Also contains a branch-and-bound max-clique solver.
    TIME : max clique is NP-hard (exponential).

5.3 CLIQUE -> INDEPENDENT-SET -> VERTEX-COVER
    (IndependentSet.java, VertexCover.java)
    WHAT : A clique in G is an independent set in complement(G); a vertex cover
           is the complement of an independent set. So we chain the reductions
           and solve all three with one solver.
    WHY  : Demonstrates the classic NP-completeness reduction chain.
    TIME : exponential (exact).

5.4 Vertex-Cover 2-approximation  (src/finserve/m5_np/VertexCover.java)
    WHAT : Greedily include both endpoints of every edge of a maximal matching.
           This yields a cover at most 2x the optimum.
    WHERE: Covering financial dependencies with a bounded quality guarantee.
    WHY  : Shows how to trade optimality for polynomial time.
    TIME : O(V + E)   GUARANTEE: solution <= 2 * OPT

====================  MODULE 6 - RANDOMIZED AND PARALLEL (CO6)  =============

6.1 Randomized QuickSort  (src/finserve/m6_random/RandomizedQuickSort.java)
    WHAT : QuickSort with a RANDOM pivot and 3-way partition; counts
           comparisons and recursion depth.
    WHERE: Ranking transactions by amount / risk.
    WHY  : Expected O(n log n) independent of input order; defeats adversarial
           worst cases.
    TIME : O(n log n) expected, O(n^2) worst   SPACE: O(log n) expected

6.2 Miller-Rabin  (src/finserve/m6_random/MillerRabin.java)
    WHAT : Probabilistic primality test. Deterministic for all 64-bit values
           using the first 12 primes as bases; also a BigInteger version with
           configurable rounds.
    WHERE: Large-number / cryptographic computations.
    WHY  : Fast and extremely reliable; only probabilistic error (2^-k).
    TIME : O(k * log^3 n)   SPACE: O(1)

6.3 Reservoir Sampling  (src/finserve/m6_random/ReservoirSampling.java)
    WHAT : Uniformly samples k items from a stream of unknown length in one
           pass and O(k) memory. An online Reservoir class handles live
           streams.
    WHERE: Continuous transaction streams.
    WHY  : Single-pass, constant memory, provably uniform.
    TIME : O(n)   SPACE: O(k)

6.4 Blelloch Scan  (src/finserve/m6_random/BlellochScan.java)
    WHAT : Work-efficient parallel prefix sum: an up-sweep (reduce) phase then
           a down-sweep phase, on a power-of-two padded array.
    WHERE: Cumulative transaction statistics (running totals).
    WHY  : O(n) work and O(log n) depth - a model parallel primitive.
    TIME : O(n) work, O(log n) depth   SPACE: O(n)

6.5 Parallel Reduce  (src/finserve/m6_random/ParallelReduce.java)
    WHAT : Tree (binary) reduction for aggregation; exposes work (n-1) and
           depth (ceil(log2 n)) and prints each level.
    WHERE: Financial aggregation (total transaction volume).
    TIME : O(n) work, O(log n) depth

6.6 Brent's Theorem  (src/finserve/m6_random/BrentTheorem.java)
    WHAT : Bounds parallel time T_P <= W/P + D, then computes speedup
           S = W/T_P and efficiency E = S/P.
    WHERE: Sizing parallel transaction processing.
    WHY  : Relates work, depth and processors - key to parallel algorithm
           analysis.

 7. EXPECTED REVIEWER / VIVA QUESTIONS WITH ANSWERS
--------------------------------------------------------------------------------

 --- GENERAL / PROJECT-LEVEL ---

Q1. What is your project about in one line?
A.  FinServe is a Java, menu-driven banking analytics platform that demonstrates
    26 DSA algorithms (modules M1-M6) on realistic customer, account,
    transaction, document and fraud data.

Q2. Why did you choose Java?
A.  Java gives a clean package structure, strong typing, a rich standard library
    (java.util, java.math) and runs anywhere with the JVM. It also enforces good
    OOP design through the domain model classes.

Q3. How is the project organised?
A.  By module: src/finserve/m1_strings ... m6_random. Shared entities live in
    model/, helpers in util/, and Main.java drives the interactive menu. Each
    algorithm is in its own class, so every concept is separately examinable.

Q4. Where is the data coming from?
A.  DataStore.java creates all seed data in memory (8 customers, 8 accounts,
    10 transactions, 3 documents, 5 fraud patterns) plus graph generators, so
    the project runs with no database.

Q5. Which module was the hardest and why?
A.  M2's SA-IS: it needs L/S-type classification, LMS substring naming and two
    induced-sorting passes. I verified it against a naive suffix-array builder
    on 14,400 random strings to be sure it is correct.

Q6. How do you know your implementations are correct?
A.  Algorithms with a simple reference version are cross-checked at runtime
    (SA-IS vs naive suffix array, DPLL vs brute force, quicksort vs
    Arrays.sort, max-flow results across three algorithms all equal).

 --- MODULE 1 - STRINGS ---

Q7. Explain KMP. What is the failure function for?
A.  The LPS/failure array stores, for each prefix, the length of the longest
    proper prefix that is also a suffix. On a mismatch it tells us how far to
    slide the pattern without re-checking matched characters, giving O(n+m).

Q8. KMP vs Z-function vs Rabin-Karp - when to use which?
A.  KMP and Z are both linear and exact. Z is convenient for pattern+text via a
    separator. Rabin-Karp wins when searching many patterns of the same length
    or when you can exploit rolling hashes, but has a worst-case O(nm).

Q9. How does Aho-Corasick find many patterns at once?
A.  It builds a trie of all patterns and adds failure links (BFS). Scanning the
    text follows the automaton; whenever a terminal state is reached we report
    the patterns that end there. Total cost is linear in text length plus
    matches.

Q10. What is the failure link in Aho-Corasick?
A.  It points to the longest proper suffix of the current prefix that is also a
    prefix of some pattern - the same idea as KMP generalised to a trie.

 --- MODULE 2 - SUFFIX STRUCTURES ---

Q11. What is a suffix array and why is it useful?
A.  It is the sorted list of all suffix starting positions. It lets us binary
    search for substrings, compute LCP-based repeated patterns, and index text
    compactly - a space-efficient alternative to suffix trees.

Q12. Explain the prefix-doubling construction.
A.  Initially rank suffixes by their first character. Then repeatedly sort by
    the pair (rank[i], rank[i+k]); each round doubles the compared length, so
    after O(log n) rounds suffixes are fully sorted.

Q13. What does SA-IS do differently and why is it O(n)?
A.  SA-IS classifies positions as L-type/S-type, finds LMS (Left-Most-S)
    substrings, sorts them recursively, and then INDUCES the full suffix array
    in two linear passes. It avoids comparison sorting entirely, achieving O(n).

Q14. What is the LCP array and Kasai's trick?
A.  LCP[i] = longest common prefix of sa[i-1] and sa[i]. Kasai's observation is
    that LCP decreases by at most 1 between adjacent starting positions, so a
    single linear scan with a running h value computes all values in O(n).

Q15. What is a suffix automaton?
A.  The minimal DFA recognising all substrings of a string, built online in
    O(n). Each state has a length and a suffix link; the number of distinct
    substrings equals sum over states of (len[v] - len[link[v]]).

--- MODULE 3 - DP ---

Q16. State the edit-distance recurrence.
A.  d[i][j] = min( d[i-1][j]+1, d[i][j-1]+1, d[i-1][j-1] + (a[i]!=b[j]) ).
    The first two are insert/delete, the last is match/substitute.

Q17. Difference between Levenshtein and Damerau-Levenshtein?
A.  Damerau adds a fourth operation: transposition of two adjacent characters,
    computed using the d[i-2][j-2] cell. It is better for typing errors.

Q18. Why weighted edit distance?
A.  In financial data, corrections have unequal costs (deleting a digit may be
    worse than substituting a similar one). Weighted/ digit-aware distance
    reflects that.

Q19. Explain the bitmask DP assignment.
A.  Let dp[mask] = min cost to assign the first popcount(mask) people to the
    tasks in mask. Transition: add the next person to any unused task. Answer
    dp[(1<<n)-1]. O(n 2^n).

Q20. When is matrix-chain DP applicable?
A.  When a chain of matrices is multiplied and the order of multiplication
    (parenthesisation) changes the number of scalar operations - optimal
    substructure over intervals.

--- MODULE 4 - FLOW ---

Q21. What is max-flow and the residual graph?
A.  Max-flow is the largest amount that can be sent from source to sink
    respecting capacities. The residual graph holds remaining forward capacity
    and back-edges that allow flow to be "cancelled".

Q22. Ford-Fulkerson vs Edmonds-Karp vs Dinic.
A.  FF picks any augmenting path (DFS) - O(E*F). EK picks the shortest (BFS) -
    O(VE^2), polynomial. Dinic uses level graphs and blocking flows -
    O(V^2 E), and O(E sqrt V) for unit-capacity graphs.

Q23. Why must we add reverse (back) edges?
A.  They let the algorithm reroute earlier decisions. Without them a greedy
    augmentation could get stuck at a sub-optimal flow.

Q24. State the max-flow min-cut theorem.
A.  The maximum flow value equals the minimum s-t cut capacity. After max-flow,
    the vertices reachable from s in the residual graph define a minimum cut.

Q25. How does bipartite matching relate to flow?
A.  Add a super-source to all left vertices (cap 1), edges for allowed pairs
    (cap 1), and each right vertex to a super-sink (cap 1). The max-flow equals
    the maximum matching. Kuhn's algorithm is the direct combinatorial version.

--- MODULE 5 - NP ---

Q26. What makes 3-SAT NP-complete?
A.  It is in NP (a satisfying assignment is checkable in polynomial time) and
    every NP problem reduces to SAT (Cook-Levin). 3-SAT is the canonical
    restriction used for reductions.

Q27. Explain the 3-SAT to CLIQUE reduction.
A.  Create 3 vertices per clause (one per literal). Add an edge between two
    vertices iff they are in different clauses and are not complements. A clique
    of size m (= number of clauses) selects one literal per clause consistently,
    giving a satisfying assignment.

Q28. How do CLIQUE, INDEPENDENT-SET and VERTEX-COVER relate?
A.  An independent set in G is a clique in complement(G). A vertex cover C is
    exactly the complement of an independent set: V\C is independent. So all
    three are inter-reducible.

Q29. Explain the vertex-cover 2-approximation.
A.  Find a maximal matching (greedily). Take BOTH endpoints of every matched
    edge. No edge is left uncovered, and the optimum must contain at least one
    endpoint per matched edge, so the answer is within 2x the optimum.

Q30. Why approximate instead of solving exactly?
A.  Vertex cover (and clique, SAT) are NP-hard; exact algorithms are
    exponential. Approximation gives a polynomial solution with a proven
    quality guarantee.

--- MODULE 6 - RANDOMIZED / PARALLEL ---

Q31. Why randomize the quicksort pivot?
A.  A fixed pivot can be forced into O(n^2) by adversarial input. A random
    pivot makes the expected time O(n log n) for ANY input.

Q32. How does Miller-Rabin work?
A.  It writes n-1 = 2^r * d and tests witnesses a: compute a^d mod n; if it is
    not 1 or -1, square repeatedly. Passing for many bases implies n is prime
    with probability 1 - 2^-k. Using the first 12 primes makes it deterministic
    for all 64-bit integers.

Q33. What is reservoir sampling and why is it uniform?
A.  Keep the first k items; for the i-th item (i>k) replace a random reservoir
    slot with probability k/i. By induction each item has probability k/n of
    being in the final sample, using O(k) memory in one pass.

Q34. Explain Blelloch's scan.
A.  Up-sweep: build a reduction tree so each node holds the sum of its leaves.
    Down-sweep: push prefix values back down, replacing internal nodes with
    exclusive prefixes. Result is an exclusive prefix sum in O(n) work and
    O(log n) depth.

Q35. What is Brent's theorem?
A.  For work W, depth D and P processors, T_P <= W/P + D. It gives a simple
    upper bound on parallel time and is the basis for speedup (W/T_P) and
    efficiency (S/P) analysis.

Q36. Difference between work, depth and parallel time?
A.  Work = total operations (sequential time). Depth (span) = longest
    dependency chain (time with unlimited processors). Parallel time is bounded
    by max(W/P, D), and Brent gives W/P + D.

 --- CROSS-CUTTING / DESIGN ---

Q37. Which module uses which data structure?
A.  M1: tries + arrays; M2: rank arrays, suffix automaton transitions; M3: DP
    tables / bitmasks; M4: adjacency-list flow networks; M5: graphs + adjacency
    matrices; M6: arrays, heaps/queues implicitly through recursion.

Q38. What are the limitations of your project?
A.  Inputs are in-memory seeds (no persistence); NP module is exponential and
    only practical for small instances; parallel algorithms are simulated
    sequentially rather than truly multi-threaded.

Q39. If I give you a 10-million character document, which index would you use?
A.  SA-IS to build the suffix array in O(n), then binary search + LCP for
    substring/range queries; Aho-Corasick if I need to find many known patterns.

Q40. How would you extend the project?
A.  Add file/database persistence, real multi-threaded implementations using
    java.util.concurrent (ForkJoin / parallel streams), an HTTP/REST layer, and
    more fraud models (e.g. graph community detection).
